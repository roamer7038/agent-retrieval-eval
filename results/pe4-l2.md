# PE4: エージェント経由の予備（L2、開発用）

事前実験 PE4 の結果。L2（Claude Code ＋ 標準の道具 ＋ 系統の代表の道具 1 つ）の条件を実装し、ローカル LLM で手順を確かめ、少量の Sonnet で課題文と道具の説明を点検した。実装は [`harness/run.py`](../harness/run.py)（条件）、[`docker/l2/`](../docker/l2/)（イメージ）、[`tasks/env/`](../tasks/env/)（環境の説明）、[`grade/`](../grade/)（採点と集計）。Sonnet の 44 セッションの採点は [`pe4-l2.jsonl`](pe4-l2.jsonl)（トランスクリプトは公開しない）。事実（測った値）と解釈は節を分ける。

**ローカル LLM（qwen3.8:27b）の結果は手順の確認にだけ使い、効果の大きさの根拠にしない**（モデルの能力が Sonnet と違うため）。効果の大小に触れるのは Sonnet の節だけである。

## 1. 条件の実装

### 1.1 条件

統括の決定（PE3 の L1 の結果から選んだ系統の代表）に沿って、8 条件を実装した。

| 条件 | 足す道具 | 系統 | 渡し方 | イメージ |
|---|---|---|---|---|
| A0 | ―（題材を渡さない） | 記憶の上限 | ― | `are-l2-base:pe4` |
| A1 | ―（標準のみ） | 標準 | Read・Grep・Glob・Bash | `are-l2-base:pe4` |
| A2 | universal-ctags | シンボル索引 | CLI（`readtags`） | `are-l2-ctags:pe4` |
| A3 | zoekt | 構文・字句 | CLI（`zoekt`） | `are-l2-zoekt:pe4` |
| A4 | semble ＋ qmd | BM25・混合 | semble は CLI、qmd は MCP | `are-l2-semble-qmd:pe4` |
| A5 | codebase-memory-mcp | グラフ | MCP | `are-l2-codebase-memory-mcp:pe4` |
| A6 | Serena | LSP | MCP | `are-l2-serena:pe4` |
| A7 | wikictl | 自作 | CLI | `are-l2-wikictl:pe4` |

- **本来の渡し方**: MCP のサーバを持つ道具（codebase-memory-mcp・Serena・qmd）は `--mcp-config` で MCP として渡し、CLI の道具（readtags・zoekt・semble・wikictl）は PATH に置く。qmd は CLI と MCP の両方を持つが、MCP のサーバ（`qmd mcp`）と Claude Code のプラグインを配っているので MCP を本来の形とした。
- **イメージ**: 条件ごとのイメージは PE1（L0）の道具のイメージ（`are-l0-<道具>:pe1`）に Claude Code と標準のコマンド（ripgrep・fd・tree・less）を足したもの。標準の部分は全条件で同じ層になる。A4 だけは semble の導入を qmd のイメージに写した 1 つのイメージにした。
- **当てはまらない組み合わせ**: 計画どおり c3（Linux）は L0・L1 のみ。qmd は c3（reStructuredText）に、Serena は c3・c4 に、wikictl は c2・c3 に当てはまらない。`harness/run.py plan` が条件 × 題材の表と理由を出す。

### 1.2 索引の渡し方

索引は **PE1（L0）が作ったものをそのまま**使い、セッションには **overlay 越しに**渡す（下層＝L0 の索引、上層＝そのセッションの作業ディレクトリ）。

- 道具は書ける（qmd・codebase-memory-mcp の SQLite、Serena の作業ファイルは書き込みを要求する）が、**L0 の索引そのものは変わらない**。セッションが終われば上層は記録として残る。
- **セッションの中で索引を作らせない**ために、条件が PATH に置くのは環境の説明に書いたコマンドだけにした（`readtags` は置くが `ctags` は置かない、`zoekt` は置くが `zoekt-index` は置かない）。
- Serena だけは索引を題材の木の中（`<リポジトリ>/.serena`）に持つので、L0 の上層からそのディレクトリだけをセッションの題材の複製に写す。L0 の更新の試験で変わったファイル（`areL0Probe`）は写さない。
- L0 の測定の記録（索引の下の `l0/`）はセッションの視界から消す。

### 1.3 パス

題材の複製を `/corpus`（課題文が指すパス）と `/work`（L0 が索引を作ったときのパス）の両方にマウントする。同じファイルで、索引の中のパスと道具の出力（readtags のタグファイル、Serena のプロジェクト、wikictl の設定、codebase-memory-mcp のプロジェクト名 `work-<リポジトリ>`、qmd の collection）はすべて `/work` を指す。採点では `/corpus/` と `/work/` のどちらの接頭辞も取り除く。

### 1.4 環境の説明

`tasks/env/A0.md`〜`A7.md`。A1〜A7 は同じ本文（題材の場所と標準の道具）で、A2〜A7 だけが**同じ形の 2 行**を足す。

| 条件 | 足した説明の文字数 | 内訳（説明・例） |
|---|--:|---|
| A2 | 168 | 115・52 |
| A3 | 161 | 110・50 |
| A4 | 210 | 129・80 |
| A5 | 206 | 137・68 |
| A6 | 172 | 121・50 |
| A7 | 153 | 116・36 |

書くのは「道具の名前」「何ができるか（索引が作成済みであること）」「呼び出し方の 1 例」だけで、手順の指南（いつ使うか、どう組み合わせるか）は書かない。A0 は題材が無いので本文が別で、課題文の規則も別にした（1.5）。

### 1.5 課題文

PE0 の課題文は「答えは題材の中から探し、題材の外の知識で推測しないでください」で始まる。A0（題材を渡さない条件）ではこれが矛盾するので、規則を条件ごとに差し替えられるようにした（`{RULE}`）。A0 は「題材は渡されていないので、知っている範囲で答えてください。分からないときは推測せず `null` にしてください」。

### 1.6 記録

`grade/grade.py` が 1 セッションにつき 1 行で出す（PE4 で足したもの）。

| 項目 | 内容 |
|---|---|
| `tool_calls` | 道具ごとの呼び出し回数（Claude Code の道具と MCP の道具。MCP はトランスクリプトの `tool_use` の `mcp__<サーバ>__<道具>` から数える） |
| `tool_bytes` | 道具ごとに**返ったデータの大きさ**（`tool_result` の本文のバイト数） |
| `shell_by_cmd` | シェルのコマンドごとの回数（記録用の包みを通ったもの） |
| `per_tool`・`added_tool_used`・`added_tool_calls`・`added_tool_bytes` | 条件が**足した道具**を使ったか、何回呼んだか、何バイト返ったか（CLI は包みの記録、MCP はトランスクリプト） |
| `mcp_servers` | セッション開始時の MCP サーバの名前と状態 |
| 既存 | 正否、根拠、トークン、USD、実時間、ターン、シェルのコマンド数・時間・出力量 |

`grade/summarize.py` は条件ごとに「道具を使ったセッションの割合」「呼び出し回数の中央値」「返ったデータの中央値（KB）」を表に足した。これで**割り付けどおりの分析**と**足した道具を使ったセッションだけの分析**を分けて出せる。

## 2. 事実: ローカル LLM での手順の確認

`local:qwen3.8:27b`（Ollama、別のマシン）で、c1 の S1（識別子あり）を 8 条件、S8（存在しないもの）を 3 条件流した。**目的は手順の確認**で、条件の間の差は読まない。

### 2.1 通ったこと

| 確認したいこと | 結果 |
|---|---|
| 8 条件すべてでセッションが立ち上がる | 立ち上がった。MCP の 3 条件（A4 の qmd、A5、A6）はいずれも `status: connected` で、道具の一覧に `mcp__<サーバ>__*` が並んだ |
| 索引が読める | readtags・zoekt・semble・wikictl・qmd・search_graph・find_symbol のいずれも、L0 の索引を overlay 越しに引けた |
| 記録が欠けない | `answer.json`・トランスクリプト・コマンドの記録・時間・トークンは、A0 の打ち切りを除いて欠けなし |
| 道具の使用が数えられる | CLI は包みの記録から、MCP はトランスクリプトから数えられた（A2 は readtags を 1 回、A6 は Serena の道具を 2 回で 5.5KB） |
| 採点 | S1（`path`）・S8（`null`）とも自動で採点でき、`grade/selfcheck.py` は開発用の 316 問（632 の合成セッション）で誤りなし |

### 2.2 ここで見えた手順の問題

- **A0（題材なし）が終わらない**。`/corpus` を探し続け、25 分の上限に達した。課題文の規則を条件ごとに分けた（4 節の #2）。
- **S9（文書→コード）が 20 分で終わらない**。トランスクリプトは 904 行で、同じ探索を繰り返していた。**ローカル LLM は L2 の難しいシナリオの確認には使えない**ので、S9 の確認は Sonnet で行った（3 節）。
- 1 セッションが 250〜360 秒（Sonnet の 20 倍以上）。ローカルは 1 本ずつしか流せない（PE0 の結論）ので、**条件 × 問題を広く流す用途には向かない**。

### 3.3 費用の内訳（重要）

条件ごとの費用の差は、**この規模では道具の使い方よりプロンプトのキャッシュの状態で決まっている**。S1 識別子ありの 8 セッションのトークン:

| 条件 | 入力 | 出力 | キャッシュ読み | キャッシュ書き | USD |
|---|--:|--:|--:|--:|--:|
| A0 | 4 | 182 | 24,033 | 1,220 | 0.0115 |
| A1 | 6 | 249 | 25,510 | 13,111 | 0.0600 |
| A2 | 6 | 241 | 37,298 | 1,696 | 0.0167 |
| A3 | 6 | 298 | 37,311 | 1,704 | 0.0173 |
| A4 | 6 | 261 | 31,704 | 16,207 | 0.0738 |
| A5 | 6 | 314 | 38,040 | 19,405 | 0.0884 |
| A6 | 6 | 300 | 43,433 | 22,080 | 0.1000 |
| A7 | 6 | 275 | 37,284 | 1,685 | 0.0170 |

同じ prefix を持つ条件（A1・A2・A3・A7 は同じ標準の道具の定義）では、**最初に流した条件がキャッシュを書き、あとの条件は読むだけ**になる。A1 が高いのは順番が先だったからで、道具の効果ではない。MCP の条件（A4・A5・A6）は道具の定義の分だけ prefix が別になり、毎回書き込みが起きる。**MCP の道具の定義は、使わなくても入力に乗る**（A6 は 21 個の道具の定義で読み 43k）。

### 3.4 費用と時間（まとめ）

| 量 | 最小 | 中央 | 最大 | 合計 |
|---|--:|--:|--:|--:|
| 1 セッションの USD（44 件） | 0.011 | 0.024 | 0.210 | **2.290** |
| 1 セッションの実時間（秒） | 3.8 | 10.1 | 69.3 | ― |

- c1 の 41 セッションで 1.852 USD、c4 の 3 セッションで 0.438 USD。**上限 5 USD に対して 46%** で止めた。
- 実時間には、MCP のサーバの起動（Serena の gopls、qmd のモデルの読み込み）と題材の複製が入る。複製はセッションの外で行い（c2 の 2.3GB で 4.9 秒、c4 で約 3 秒）、`wall_ms` には入らない。
- 参考: 同じ 4 問をローカル LLM（qwen3.8:27b）で流すと 1 セッション 250〜360 秒で、Sonnet の 20 倍以上かかる。**手順の確認にはローカル、効果の測定にはクラウド**という分担は妥当である。

### 3.5 反復（PE5 の較正の下見）

同じ問題（S1 識別子あり）・同じ条件を 4 回ずつ流した（A1・A3・A6、計 12 セッション。うち 1 回目は 3.1〜3.4 と同じもの）。

| 条件 | 1 回目 USD | 2〜4 回目 USD | 2〜4 回目の sd(log USD) | 実時間の平均 s | sd(log 実時間) | 正否 |
|---|--:|--:|--:|--:|--:|---|
| A1 | 0.0600 | 0.0124 | 0.011 | 6.1 | 0.203 | 4/4 |
| A3 | 0.0173 | 0.0121 | 0.031 | 6.3 | 0.301 | 4/4 |
| A6 | 0.1000 | 0.0175 | 0.041 | 9.1 | 0.178 | 4/4 |

1 回目にキャッシュの書き込み（A1 13,111・A6 22,080 トークン）が起き、2 回目以降は 242〜522 トークンに落ちる。**同じプロンプトを繰り返すと費用が 4〜6 分の 1 になる**。

- **費用のばらつきは、繰り返しの中ではほとんど無い**（sd(log USD) ≤ 0.04）が、**キャッシュの状態でその 20 倍以上動く**。1 問あたりの費用を主要な指標にする以上、キャッシュの扱いを事前登録で決める必要がある（6.2）。
- **実時間のばらつきは sd(log) で 0.18〜0.30**（おおよそ ±20〜35%）。反復で減らせるのはこの部分である。
- 12 セッションすべて正答。正答のばらつき（σ²_rep）はこの問題では 0 で、**天井効果は L2 でも出ている**（計画の想定どおり）。

## 4. 見つかった不具合と直した点

| # | 症状 | 原因 | 直し方 |
|---|---|---|---|
| 1 | `qmd query`（既定）が**永久に止まる** | qmd の設定は埋め込み・展開・再順位付けの 3 つのモデルを指すが、PE1 のイメージには前 2 つしか入れていない（L1 は `--no-rerank` で使うため）。外に出られないので取得が終わらない | 再順位付けのモデル（Qwen3-Reranker-0.6B-Q8_0、版とハッシュを固定）を A4 のイメージに入れた |
| 2 | 課題文が A0 と矛盾する | 「答えは題材の中から探し…」が全条件に固定だった | 規則を条件ごとに差し替えられるようにし、A0 は「知っている範囲で答え、分からなければ `null`」にした |
| 3 | 道具の索引の場所が L0 のパス（`/index`）のまま | L0 のイメージの環境変数が残る。MCP の条件では `mcp.json` の env で上書きされるので気づきにくい | 索引と設定の場所はコンテナの環境変数でも上書きする（HOME と PATH は `mcp.json` だけ） |
| 4 | セッションが索引を作れてしまう | 道具のディレクトリを PATH に足すと `ctags`・`zoekt-index` も入る。MCP でも `index_repository` が見える | PATH に置くのは説明に書いたコマンドだけにし、MCP は索引を作る道具（`index_repository`・`delete_project`・`ingest_traces`・`manage_adr`）を `--disallowedTools` で外した |
| 5 | Serena の `execute_shell_command` | シェルの記録（包み）を迂回して測定が壊れる | `--disallowedTools` で外した。ただし `--context ide-assistant` では元から現れないことを確認した |
| 6 | `shell_by_cmd` がどのコマンドも 1 と数える | 集計の書き方の誤り（辞書内包の中で自分を参照） | `collections.Counter` にした |
| 7 | L0 の測定の記録が索引の中に見える | `index/l0/` に L0 の問い合わせの出力が残っている | セッションの overlay の上層で消してから渡す |
| 8 | 記録のディレクトリが増え続ける | 題材の複製が 1 セッションに c4 で 0.85GB・c2 で約 1.5GB 残る | セッションの後に複製を消す（`ARE_KEEP_CORPUS=1` で残せる）。複製そのものは速い（c2 の 2.3GB で 4.9 秒。git のオブジェクトはハードリンク） |
| 9 | セッションの記録のディレクトリが消せない | overlay の作業ディレクトリを核が root の持ち物で作る | 後始末でコンテナの中の root から消す |

このほか、**道具そのものは変えていない**（版・設定は PE1 のまま）。qmd の再順位付けのモデル（#1）だけがイメージへの追加である。

## 5. PE4 の進む条件

条件は「**課題文の曖昧さによる誤答が Claude で見られない**」。

| 観点 | 事実 | 判定 |
|---|---|---|
| 誤答 | Sonnet の 40 セッション（題材のある条件）で誤答 0。4 問 × 8 条件（c1）、1 問 × 3 条件（c4）、反復 9 セッションのすべてで正答 | 満たす |
| 回答の形 | `answer.json` の欠け・形式の誤り 0 件。パスの書き方（`/corpus` からの相対、リポジトリ名つき）の取り違えも 0 件 | 満たす |
| 言い換えの問題 | S1 の言い換え（識別子を出さず、処理の内容だけを書いた問い）でも 7 条件すべて正答し、根拠のファイルも一致 | 満たす |
| 長い定義を含む問題 | S9（「値を読み書きするか、値によって処理を変えるファイル。名前が一覧・表・コメントに並ぶだけのファイルは含めない」）でも、除外の指示どおりに `cli.go`・`help.go` を外して正答した（A3 の記録に判断の過程が残っている） | 満たす |
| 例外 | **A0（題材なし）は S8（正解が `null`）で中身を見ずに「正答」する**。記憶の上限を測る条件と「存在しないことの確認」の組み合わせは、正答率をそのまま比べられない | 事前登録で扱いを決める必要がある |

したがって PE4 の進む条件は満たしている。ただし次の 2 点は PE5 と事前登録で決める。

1. **A0 × S8 の扱い**。A0 は「分からなければ `null`」と指示されるので、S8 では常に正答になる。A0 の比較から S8 を外すか、A0 の指示を変える（分からないことを別の値で表す）か。
2. **道具の使用率の低さ**。足した道具を呼んだのは 26 セッション中 11。使われない条件は「道具の効果」を推定するための実質の n が小さくなる。PE5 で条件ごとの使用率を測り、**割り付けどおりの分析**（意図による分析）と**使ったセッションだけの分析**の 2 本立てを事前登録に書く。

### 5.1 限界（本番に持ち越す）

- **道具の説明の分量**は揃えたが、**MCP のサーバは自分の説明を送る**。qmd の MCP は「`intent` を必ず付けよ」などの指示を接続時に送り、Serena は 21 個、codebase-memory-mcp は 17 個の道具の定義を送る。CLI の条件にはこれがない。渡し方を揃えた比較は行わない（計画どおり）が、**入力のトークンの差**として費用に出る（3.3）。
- **Serena には編集の道具（`replace_symbol_body` など）が含まれる**。検索の実験としては余分だが、道具本来の形を崩さないために残し、使われた道具を記録する方針にした。`execute_shell_command` だけは記録を迂回するので外した（`--context ide-assistant` では元から現れない）。
- **索引の中身は PE1 のまま**で、L0 の更新の試験の痕跡（`areL0Probe`）を含む。統括の決定どおり本番の前に作り直す。

## 6. PE5（較正）で測るべき量

PE5 の目的は「本番の問題数と反復数を決めるための分散の推定」である。PE4 の実装のままで測れるように、測る量と測り方を先に決めておく。

### 6.1 測る量

| 記号 | 量 | 測り方 |
|---|---|---|
| σ²_rep | 同じ問題・同じ条件を繰り返したときのばらつき | 代表の問題 × 条件を r 回繰り返す。主要な指標は log(1 問あたりの USD) と log(実時間)、正否は 0/1 |
| σ²_q | 問題の間のばらつき（ランダム効果） | 同じ条件で問題を変える。σ²_q は σ²_rep より大きいはずで、どちらが大きいかで「問題を増やす」か「反復を増やす」かが決まる |
| σ²_c×s | 条件 × シナリオの交互作用の大きさの当たり | RQ1 の仮説は交互作用なので、検出したい効果量をこの尺度で決める |
| p・ICC | 正答率と、同じ問題の中の相関 | 同等性の検定（±5 ポイント、TOST）の検出力の計算に使う |

推定は、費用と時間は `log(y) ~ 条件 + (1|問題)`、正答は混合効果ロジスティック回帰（分析計画と同じ形）で行い、`σ_問題`・`σ_残差` を取り出す。

### 6.2 反復の設計

- 反復は**同じ条件・同じ問題**を r 回。r = 5、代表の問題は 1 題材あたり 2 問（差の出るシナリオ S1・S3 と、差の出にくい S5 か S6 を混ぜる）。
- **プロンプトキャッシュの影響を避ける**。同じプロンプトを続けて流すとキャッシュの読み取りが増えて費用が下がり、σ²_rep を過小に見積もる。反復は条件をまたいで順に回し（同じセッションを連続させない）、`cacheReadInputTokens`・`cacheCreationInputTokens` を分けて記録したうえで、キャッシュを含む費用と含まない費用の両方を出す（`grade/grade.py` はすでに内訳を持っている）。
- 1 セッション＝1 問・1 コンテナで、コンテナも索引の overlay もセッションごとに作り直すので、セッションの間に状態は残らない（残るのは Ollama・Anthropic 側のキャッシュだけ）。
- PE4 の実測（3.5）では、**条件の prefix を最初に流したセッションだけが 4〜6 倍高い**。PE5 では次の 3 つを比べ、事前登録に書く形を決める。(a) 条件ごとに捨てるセッションを 1 本流してからそろえて測る（温めてから測る）、(b) 条件の順番を無作為にしてキャッシュの状態を共変量に入れる、(c) キャッシュを使わない費用（`cacheCreation` を入力の単価で数え直した値）を主要な指標にする。

### 6.3 反復数と問題数の決め方

PE5 の σ を使ってシミュレーションする。1 セッションの費用を c、予算を B とすると、使えるセッション数は N = B / c。PE4 の実測では c は 0.011〜0.21 USD（中央 0.028、温まった状態で 0.012〜0.018）なので、PE5 の 25 USD では **N はおよそ 150〜2,000**。N を「問題数 n × 条件数 8 × 反復 r」に割り振り、n と r を振って検出力を計算する。σ²_q が σ²_rep より大きい限り、同じ N なら r を増やすより n を増やす方が有利になる（反復は同じ問題の中の分散しか減らさない）。この形を PE5 の報告に入れ、事前登録の「問題数」を決める根拠にする。

### 6.4 PE5 で一緒に確かめること

- **道具を使ったセッションの割合**（`added_tool_used`）。割り付けどおりの分析と、使ったセッションだけの分析の両方を出すため、条件ごとの使用率の信頼区間が要る。使用率が低い条件は、効果の推定に必要な N が跳ね上がる。
- **立ち上げの時間**。MCP の条件はサーバの起動（Serena の言語サーバ、qmd のモデル）が 1 セッションごとに乗る。実時間の内訳として、最初の MCP の呼び出しまでの時間を別に測る。
- **失敗と停止**の率（`result_subtype`、`timed_out`、`exit`）。除外基準を事前登録に書くため。
