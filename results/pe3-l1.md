# PE3: 検索単体の予備の測定（L1、開発用）

事前実験 PE3 の結果。エージェントを介さずに「質問 → 順位付きのファイルの一覧」を取り、シナリオ別の指標と時間を測った。実装は [`l1/`](../l1/)、記録は [`pe3-l1.jsonl`](pe3-l1.jsonl)、表は `l1/grade.py` の出力。事実（測った値）と解釈（そこから何を読むか）は節を分けて書く。

LLM は使っていない。例外は qmd で、qmd は問い合わせを自前のローカル LLM で展開してから検索する。これは道具の一部として使い、記録に残した（計画の「道具の内部の LLM は道具の一部」）。

## 1. 測り方

### 1.1 L1 が測るもの

| 項目 | 内容 |
|---|---|
| 入力 | 開発用の質問 288 問のうち、L1 の対象である 238 問（S6 40 問と S8 10 問は計画どおり L1 から外す） |
| 出力 | 順位付きのファイルのパスの一覧（`<リポジトリ>/<リポジトリの根からのパス>`）。上位 50 件まで取る |
| 正解 | `tasks/dev/pe2.jsonl` の `evidence` と `evidence_rule`。ディレクトリの項目（S7）はその下のファイルに展開する。等級は付けない（すべて 1） |
| 指標 | 主 nDCG@10。副 recall@10・MRR@10。S7 は F1@10 |
| 時間 | 常駐した状態での 1 回の検索（コンテナの中で道具の呼び出しの前後を測る）。立ち上げ（コンテナ＋道具の常駐の部分）は別に記録 |

### 1.2 計測環境

PE1（L0）と同じ枠（slot）の排他ロック（`$ARE_DATA/indexes/.slot-<枠>.lock`）を使い、**1 つの枠で同時に 1 つだけ**動かした。さらに PE3 では枠をまたいだ同時実行も行わず、`l1/pe3.sh` が全体を順に流している（時間の測定に他の測定が重ならないようにするため）。1 回の制限は 8 vCPU・メモリ 16GiB・ネットワークなし。既定から外した設定は次のとおり（統括の決定と PE1 の記録に沿う）。

| 道具 | 題材 | 既定から外した設定 | 理由 |
|---|---|---|---|
| semble | c3 | メモリ 32GiB、L0 の索引 `c3.mem32g` | 統括の決定（c3 の混合系は 32GiB で semble） |
| codebase-memory-mcp | c3 | `CBM_MEM_BUDGET_MB=12288`、L0 の索引 `c3.mem12g` | 道具の既定の予算 4GiB では L0 で失敗 |
| graphify | c3 | `GRAPHIFY_MAX_GRAPH_BYTES=4GB`、メモリ 32GiB | `graph.json` が 1.72GB で道具の既定の上限 512MB を超える |
| serena | c2 | 言語サーバは Go のみ | 統括の決定（c2 は Go のみを主とする） |

索引は **PE1 が作ったものをそのまま使う**。したがって、L0 の差分更新の試験で 2 つのファイルに足した `areL0Probe`（コードの関数 1 つと文書の段落 1 つ）が、どの道具の索引にも同じように入っている。

### 1.3 常駐

(tool, corpus) の組ごとにコンテナを 1 つ立ち上げたままにし、`l1/worker.py` に質問を 1 問ずつ渡す。常駐の度合いは道具によって違い、それ自体が結果である。

| 常駐の形 | 道具 | 内容 |
|---|---|---|
| プロセスの常駐（MCP） | codebase-memory-mcp | 道具本来の渡し方である MCP のサーバを立ち上げたままにし、`search_graph` を呼ぶ |
| プロセスの常駐（本体） | Serena | `SerenaAgent` を作ったままにし、言語サーバを上げ続ける |
| コンテナの常駐のみ | semble・ck・qmd | 常駐の口（デーモン・サーバ）が CLI に無く、1 回ごとにモデルと索引を読み直す |
| 常駐は不要 | それ以外 | 索引のファイルを読むだけ、または索引を持たない |

## 2. 事前登録できる規則

L1 を決定的にするために、質問の変換・順位・打ち切り・同点の規則を先に決めた。実装は `l1/tasks.py`（変換）と `l1/worker.py`（順位）にあり、この節はその要約である。

### 2.1 質問の変換の規則

質問は 3 つの形のどれかに変換する。**どの形を使うかは道具の問い合わせの口で決まり、質問では決まらない**。

| 形 | 内容 |
|---|---|
| `ident` | 質問の識別子を、現れる順に。識別子は、バッククォートの中の `[A-Za-z_][A-Za-z0-9_]{2,}` のうち言語の予約語（`struct`・`type` など）と題材の名前（`wikictl`・`grafana` など）でないもの、続いてバッククォートの外の snake_case・CamelCase の語（4 文字以上）。**パスを表すバッククォート（`/` を含む）は飛ばす**（読み手への道しるべであって、探す対象の記号ではないため）。識別子が無ければ空になる |
| `terms` | `ident` に加えて質問の内容語。日本語は漢字・カタカナの 2 文字以上の連なりのうち定型の語（「ソースコード」「ファイル」など）でないもの、英語は 3 文字以上の語のうちストップワードでないもの。上限 12 語 |
| `nat` | 質問そのもの（1 つの文字列） |

道具ごとの割り当てと理由:

| 系統 | 道具 | 形 | 理由 |
|---|---|---|---|
| 標準 | grep（`git grep`） | terms | 字句の一致しかできない。日本語の文をそのまま渡しても 1 つの固定文字列にしかならない |
| シンボル索引 | ctags・GNU global・cscope | ident | 索引の鍵が識別子で、自然文を受ける口が無い |
| 構文・字句 | ast-grep | ident | 問い合わせがパターン言語であり、識別子を置くのが本来の使い方 |
| 構文・字句 | probe・zoekt | terms | 字句・BM25 の検索器で、語の集合を受ける |
| BM25・混合 | qmd・semble・ck | nat | 自然文を受ける口が本来の渡し方（qmd は自前で展開し、semble は「Natural language or code query」） |
| グラフ | codegraph・graphify | ident | 問い合わせがノード（記号）の名前 |
| グラフ | codebase-memory-mcp・GitNexus | nat | どちらも概念の問い合わせを BM25・ベクトルで解く口が本来の渡し方（GitNexus の help は "Search ... related to a concept"） |
| LSP | Serena | ident | `find_symbol` の名前パターン |
| 自作 | wikictl | terms | `wikictl grep` は字句の検索 |

識別子の形しか受けない道具は、言い換えの質問で**問い合わせが空になる**。これは失敗ではなく道具の性質なので、`empty_query` として記録し、0 点として集計し、件数を報告する。

**質問の言語**。実験の質問の言語は日本語なので、`terms` と `nat` の道具の**主の条件は日本語の質問**（`query_lang=ja`）である。確認済みの英語の対訳を**第 2 の条件**（`query_lang=en`）として別に測り、日本語の質問が英語の題材に対して不利になる度合いを、仮定ではなく測った値で報告する。`ident` の形は ASCII なので 1 回だけ（`query_lang=id`）。

### 2.2 順位に直す規則

道具の返す並びがそのまま順位である。順位の無い道具は次の規則で順位にする。

| 規則 | 道具 | 内容 |
|---|---|---|
| 定義 → 参照 | ctags・GNU global・cscope・Serena | まず定義の結果、次に参照の結果。各部分の中は道具の出力の順（3 つともパスの順に出す） |
| 一致の数 → パス | grep・wikictl・ast-grep | 一致した問い合わせの語の数の降順、次に一致の数の降順、次にパスの昇順。計画の「標準」の規則を、一致の有無しか返さない道具すべてに使う |
| 道具の順 | probe・zoekt・qmd・semble・ck・codebase-memory-mcp・codegraph・graphify・GitNexus | codegraph は道具のスコア、graphify は記号を起点とした幅優先の並び、GitNexus は `definitions` の後に `process_symbols` |
| 識別子が複数 | 全道具 | 質問に現れた順に 1 つずつ問い合わせ、結果をつなぐ。既に出たパスは繰り返さない |
| リポジトリが複数（c1） | 全道具 | 比較できるスコアがある道具はスコアで併合、無い道具は `$REPOS` の順に交互に並べる（どちらのリポジトリも優遇しない） |
| 同点 | 全道具 | 上のすべての鍵が同じならパスの昇順。順位は決定的で、正解に依存しない |

### 2.3 打ち切り

1 回の検索で上位 **50 件**まで取り、指標は **10 件**で計算する（nDCG@10・recall@10・MRR@10・F1@10）。50 件は L2 でエージェントに渡せる量の上限を意識した値で、10 件は計画の指標の定義に合わせた。

### 2.4 多言語の副次の集計

統括の決定どおり、正解は「質問が対象とした言語のページ」とする。c4 で `website/content/<言語>/<残り>` を引いたとき、`website/content/<別の言語>/<同じ残り>` が正解であれば「別言語の同内容のページ」として数え、別言語も正解とした場合の nDCG@10（`ndcg10_xlang`）を副次の集計として併記する。

## 11. 天井・床の効果

**天井は無い**。全道具が nDCG@10 ≥ 0.9 に達した問題は 238 問のいずれにも無い（0/238）。L2 で心配される天井効果（wikictl-eval の標準条件は 0.84〜1.00）は、L1 の検索単体には現れない。

**床はある**。主の条件で、どの道具も 0 だった問題が 65/238（27.3%）ある。原因は 3 つで、いずれも道具の質ではなく設計に由来する。

| 原因 | 件数の目安 | 内容 |
|---|---|---|
| 言い換えの質問で識別子の形の道具に渡す問い合わせが無い | 107/119 の言い換えの質問 | 識別子索引・グラフ・LSP は構造上 0 になる。**道具の性質であり、L1 の設計どおり** |
| 日本語の語が英語の題材の本文に字句で一致しない | c2・c3 の言い換え | 計画が予告していた ja→en の不利。第 6 節のとおり、probe・semble は英語の対訳にすると +0.11〜+0.21 戻る |
| 正解の粒度が細かすぎる | S2・S7・S9 | 正解が 1 ファイルの問題では precision@10 の上限が 0.1 になり、F1 が意味を持たない（第 9 節）。S2 は「主のファイルは必須、付随の変更は任意」という PE2 の決めにより正解が 1〜4 ファイルで、言い換えの質問では手がかりが本文に残らない |

床の 65 問のうち 61 問が言い換えの質問である（識別子ありは 4 問で、いずれも S2）。**言い換えの条件は、いまの規則では「コードのシナリオではほぼ全道具が 0」という床に当たっており、L1 の比較としては情報量が乏しい**。

## 12. 解釈

- **識別子があるかどうかが、道具の系統より効く**。表し方の差（平均 +0.35）は、系統の間の差（最良 0.344 と最悪 0.028 の幅 0.32、標準・字句・混合・グラフの上位 4 つは 0.30〜0.34 に固まる）より大きい。計画の H1a（識別子を含む質問ではシンボル索引・字句が埋め込みと同等以上）は、識別子ありの条件で ctags 0.457・global 0.421・zoekt 0.620 対 semble 0.483・qmd 0.257 となり、字句（zoekt）が最も高い。H1b（言い換えでは埋め込み・混合が字句を上回る）は、言い換えの条件で semble 0.133・qmd 0.165 対 zoekt 0.050・grep 0.081 となり、**符号は仮説どおり**である。
- **コードと文書で強い系統が入れ替わる**。S1・S2・S3（コード）では cscope・codebase-memory-mcp・codegraph・zoekt・semble が上位、S4・S5（文書）では wikictl・qmd・grep・probe が上位で、シンボル索引とグラフはほぼ 0 である。**シナリオ × 手法の交互作用**は、この予備の測定でもはっきり見える。
- **索引を持つ利点は、規模が大きいほど時間に出る**。c3 で zoekt は 0.09 秒、grep は 4.67 秒、probe は 14.17 秒、ast-grep は 10.69 秒。字句の索引（zoekt）は品質でも c3 で最上位（0.424）なので、**大規模の題材では zoekt が費用対効果の点で際立つ**。
- **常駐の口があるかどうかは、道具の設計の問題である**。MCP を本来の渡し方とする codebase-memory-mcp と Serena は常駐で 1〜2 桁速くなり、CLI しか持たない semble・ck・qmd は変わらない。L2 では前者が有利になるが、これは「索引の系統の差」ではなく「渡し方の差」なので、分析では分けて書く必要がある。
- **c4 の 0.000 が 6 つある**のは、道具が文書を索引しないためで、質の低さではない。分析計画の「推定できる対比」から外すか、0 のまま入れるかで結論が変わる（第 14 節）。
- **ck は L1 では使い物にならない**。c1 でしか索引が作れず、その c1 でも nDCG@10 0.028 と最下位である。L0 の「索引が 60 分で終わらない」と合わせて、本番から外す候補である。

## 13. L2 の代表の道具を選ぶ規則（提案）

計画は「系統ごとの代表を、開発用の質問での L1 の結果から事前登録の規則で選ぶ」としている。次の規則を提案する（統括が事前登録で確定する）。

1. **候補の条件**: L0 で索引が作れた題材が 2 つ以上あること。これで ck（c1 のみ）と cscope（c3 のみ）は代表から外れる。
2. **主の順序**: 開発用の質問の主の条件での nDCG@10 を、**題材を等しく重みづけて**平均する（問題数の多い c2 に引きずられないため）。
3. **同点**: 差が 0.02 以内なら、1 回の検索の時間の中央値が小さい方。それも同じなら L0 の索引の CPU 時間が小さい方。
4. **固定**: 標準（grep）は A1 の対照として固定。LSP は Serena しかないので固定。自作は wikictl で固定（c1・c4 のみ）。混合は計画どおり内容で分ける（Markdown は qmd、コードは semble）ので選び直さない。
5. **対照**: 差の出ないシナリオでも代表を L2 に残す（計画どおり）。
6. **開発用だけで決める**。本番用の質問は事前登録の後に開く。

この規則を今回の結果に当てはめると:

| 系統 | 題材を等しく重みづけた nDCG@10（題材数） | 選ばれる代表 |
|---|---|---|
| 標準 | grep 0.295（4） | **grep**（固定） |
| シンボル索引 | ctags 0.203（4）、global 0.196（4）、cscope 0.369（1、候補外） | **ctags**（global との差 0.007 は同点の幅 0.02 以内。検索の時間の中央値はどちらも 0.00 秒、L0 の索引 CPU は c2 で ctags 9.2 秒対 global 332.7 秒なので ctags） |
| 構文・字句 | zoekt 0.304（4）、probe 0.257（4）、ast-grep 0.144（3） | **zoekt** |
| BM25・混合 | semble 0.267（4）、qmd 0.226（3）、ck 0.028（1、候補外） | **semble（コード）＋ qmd（Markdown）**（計画どおり内容で分ける） |
| グラフ | codebase-memory-mcp 0.315（4）、codegraph 0.240（4）、graphify 0.212（4）、GitNexus 0.142（3） | **codebase-memory-mcp** |
| LSP | Serena 0.210（2） | **Serena**（固定） |
| 自作 | wikictl 0.204（2） | **wikictl**（固定） |

注意: 統括の決定は「c3 のグラフ系は codegraph を代表にする」であったが、これは **L0 で c3 の索引が既定の設定で作れるのが codegraph だけ**という導入の話である。L1 の品質では codebase-memory-mcp が上（c3 でも 0.607 対 0.402）なので、**L2 の代表（c3 は L2 の対象外）と、c3 の L0・L1 で使う道具は別に書く**必要がある。
