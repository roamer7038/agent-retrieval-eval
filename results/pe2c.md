# PE2c S4 と S9 の作り直し（開発用）

2026-09-20。[PE2b](pe2b.md) の第 10 節「判断が必要な点」の 1（S4 の歩留まり）と 2（S9 の間接参照）に対する統括の決定（wiki の `projects/agent-retrieval-eval/decisions.md`）を実装し、開発用の問題を作り直した。題材と固定コミットは PE2b と同じ（C1 wikictl 66846e2 ＋ wiki 7a2a507、C2 grafana 39703a2、C3 linux 40288c9、C4 kubernetes/website 4aa397d）。ローカルの Ollama だけを使い、クラウドの LLM は使っていない。

事実と解釈を分けて書く。**監査・札付けをしたのは人ではなくエージェント（Claude）**である。利用者の監査はこれとは別に要る。

## 2. S4 の歩留まり

### 2.1 言い換えと要点の語の重なりを測る（決定 (a)）

PE2b の監査は、S4 の言い換えが理由そのものを書いてしまう誤り（`answer_in_paraphrase`）を 3 件見つけた。一意性を見る LLM の判定はこれを見つけられない。言い換えは確かに 1 つの節を指しており、ただ答えを連れているだけだからである。そこで `gen/phrase.py` に、模型を呼ばずに測る点検を足した。

> 要点 p について、`words(p) − words(識別子つきの質問)` のうち言い換えに現れる語の割合を測り、要点ごとの最大値が **0.25** を超えたら落とす。`words` は、英数字の語と、かな・漢字の並びの文字 2-gram の集合（辞書は使わない）。識別子つきの質問の語を引くのは、そこにある語は「対象の説明」であって答えではないからである。

閾値は PE2b の言い換え 13 件で較正した（`results/pe2-audit.jsonl` の `review-pe2b-3`）。

| 監査の判定 | 件数 | 重なりの値 |
|---|---|---|
| ok | 7 | 0.000〜0.154 |
| invalid（答えが言い換えに入っている） | 3 | 0.278・0.294・0.647 |
| error（要点が質問の言い直し） | 1 | 0.562 |
| invalid（別の理由：節に理由が無い、対象が違う） | 2 | 0.174・0.133（**この点検では見つからない**） |

PE2c の実行では、S4 の候補 41 件のうち 14 件（34%）が 1 回目の言い換えで閾値を超え、作り直し（模型に「答えを書かない」と伝えて引き直す）で 7 件が通った。残る 7 件は 2 回目も超えたので落ちた。点検は S4 だけに入れた（`POINT_LEAK_MAX`）。S5 は基が監査済みで、手順を尋ねる質問は目的を述べても手順を述べないため、今回は触っていない。

### 2.2 候補を 3 倍引く（決定 (b)）

題材ごとの引く深さを S4 だけ 3 倍にした（c1 8→24、c2 6→18、c4 6→18）。実際に引けたのは c1 5・c2 18・c4 18 の 41 件（PE2b は 14 件）。c2 は文書の節と Go の doc コメントを半々にする（`want_code = n // 2`）。

### 2.3 c1 は 8 基に届かない（上限の理由）

c1（wikictl の wiki）の S4 の候補は、dev の側で**節 12 件・ページ 8 件**しかない。理由を述べた節はほぼ ADR に限られ、PE2 と PE2b の監査がそのうち 9 件を落としている。引く深さを増やしても候補は増えない。試みとして、探す場所を `projects/` から `global/`・`machines/` にも広げ、見出しに理由の語が無くても本文に理由の語が 2 回あれば採る規則（c2・c4 と同じ）に変えたが、**候補は 1 件も増えなかった**（プールは 27 件のまま）。

そのうえで、PE2b が `answer_in_paraphrase` だけを理由に落とした c1 の 3 基は、節と要点は同じ監査が正しいと判断しているので、言い換えを作り直して戻した（監査の記録に `verdict: "regenerate"` を書き、`gen/common.py` の `dropped_base_ids` がそれを外す）。「監査で外した基は直さず別の候補を引く」という 2026-09-20 の決定は、代わりの候補がある題材のための決まりであり、c1 は引き尽くしている。戻した 3 基のうち 1 基は今回の監査で ok、1 基は言い換えが 2 回とも点検に掛かって落ち、1 基は答えが言い換えに入っているとして invalid にした。

結果、**c1 の S4 は 2 基が上限に近い**。本番で c1 の S4 を 10 基にすることはできない。採る道は (a) c1 の S4 を諦める（題材ごとの基の数を揃えない）、(b) wiki に ADR を足す（題材を書き換えることになるので不可）、(c) S4 の対象を「設計の理由」から「方針・規約の理由」に広げてページの種類を増やす、のどれかで、**推奨は (a)**（第 6 節）。

## 3. S9 の間接参照

### 3.1 何を足したか

PE2b の S9 は、設定のキー → 構造体のフィールド → そのフィールドを読むファイル、までを正解にしていた。値がゲッターを通って渡る場合（`cdn, _ = cfg.GetContentDeliveryURL(...)`）に使う側を拾えず、2 基を外していた。PE2c は S3 と同じ呼び出しグラフ（`gen/analyze.sh` の goanalyze）を使い、1 段先を足す。

```
設定のキー "cdn_url"                     （文字列リテラルを持つファイル: via=key）
  → 構造体のフィールド Cfg.CDNRootURL    （フィールドを読むファイル: via=field）
    → 短いメソッド Cfg.GetContentDeliveryURL
      → それを呼ぶファイル               （via=getter・PE2c で新しく入る）
```

「短いメソッド」は次をすべて満たすものに限る（`gen/cand_docs.py` の `ACCESSOR_MAX_LINES`・`returns_a_value`・`GoGraph.accessors`）。

1. **メソッド**である（値は自分のレシーバから来る。設定そのものを引数で受け取る関数は、値を渡されただけで返してはいない）
2. **12 行以内**（それ自体が仕事をしている関数ではない）
3. **error 以外の戻り値がある**（呼び手に値を返す）
4. 呼び出しが **static**（コンパイラがその関数だと決められる呼び出し。型の可能性をたどって届くだけの `vta`・`invoke`・`dynamic` は S3 と同じく `gold.optional` に入れる）
5. 呼ぶ側が生成されたコード（依存注入の配線）でない

あわせて次も直した。

- `gold.optional` が設定キーの **camelCase の綴り**（`signoutRedirectUrl`）と**構造体のフィールド名**も拾うようにした。これで PE2b が `signout_redirect_url` を error とした理由（値を持つ frontend の 3 ファイルが必須にも optional にも無い）が消えた。
- `gen/judge.py` の `s9check` が、正解の各ファイルについて**そのファイルを正解にした語**（キー・フィールド名・ゲッター名、候補の `source.gold_terms`）で抜粋を採るようにした。PE2b まではキーの文字列だけを探しており、フィールド経由のファイルには**抜粋が空のまま判定させていた**。
- S9 の選別の判定者を `gemma4:31b` 1 つにした（PE2b の測定で 2 人目は一致 0.793・κ ≈ 0 で使えなかった。決定 3 の (b)）。30 件の正解のファイルのうち判定者は 28 件を「扱っている」、2 件を「名前が並ぶだけ」とし、エージェントはどちらにも同意した（リリースノートの一覧とロードマップの表）。

質問文・`evidence_rule`・判定の指示も「値を返す短い関数を通して受け取って使う場合も含む」に揃えた。

### 3.2 間接参照の機械の正解の誤り（抜き取りではなく全数）

c2 の設定の文書にあるキーの全体（dev・test を分ける前）から、上の規則で出る 1 段先の参照を数えると **16 件**だった。少ないので抜き取りではなく全数をエージェントが監査した（`results/pe2-audit.jsonl` の `sample: fresh-pe2c-s9hop`）。

| 集合 | 件数 | 誤り | 95% 上限（片側） |
|---|---|---|---|
| ゲッター経由の 1 段先（c2 全体） | 16 | 1 | **26.4%** |

誤りとしたのは `root_url`（`Cfg.AppSubURL`）→ `HTTPServer.redirectURLWithErrorCookie` → `pkg/api/login_oauth.go` の 1 件で、戻り値のリダイレクト先を渡すだけで `root_url` の値そのものを見てはいない（境界的なので誤りに数えた）。

規則を絞る前の数字も残す。**絞る前は 24 件中 9 件（37.5%）が誤り**で、内訳は「型の可能性をたどって届くだけの呼び出し」6 件（ルーティングの表が処理関数を呼ぶ形に見える）、「値を渡すだけで受け取らない呼び出し」2 件、「error しか返さない関数」1 件だった。さらにその前（メソッドに限らず、参照も呼び出しに数えていた版）は 15 件の抜き取りで 10 件が誤りで、設定そのものを引数で受け取るヘルパ（`GetGravatarUrl(cfg, email)`）と構築子（`NewEvaluatorFactory(cfg, ...)`）がほとんどを占めた。**この 3 つの条件（メソッド・戻り値・static な呼び出し）は測って決めたものである。**

開発用の問題に入った 1 段先の参照は `cdn_url` → `pkg/api/webassets/webassets.go` の 1 件だけで、これはエージェントが本文を読んで確かめた（`cdn != ""` で分岐して `SetContentDeliveryURL` に渡す）。

### 3.3 戻した 2 基

| 基 | PE2b の判定 | PE2c |
|---|---|---|
| `dev-c2-s9-cdn-url-doc2code` | error（ゲッター経由のファイルが正解に無い） | **ok**。正解 4 件になり、`pkg/api/webassets/webassets.go` が入った |
| `dev-c2-s9-signout-redirect-url-doc2code` | error（camelCase で値を持つ 3 ファイルが必須にも optional にも無い） | **ok**。正解 5 件は同じで、frontend の 3 ファイルが optional に入った |

S9 は c1 で 5 件中 3 件の言い換えが一意性の判定で落ちる（PE2b と同じ）。c1 の語は `case_collision`・`broken_link`・`see_also` のように、名前を伏せると別の規則と区別できないものが多い。

## 6. 限界と判断が必要な点

- **監査したのは人ではなくエージェント**である。第 3.2 節の 26.4% も第 4 節の判定も、人の監査で覆りうる。
- **c1 の S4 は 2 基が上限**（第 2.3 節）。本番で題材ごとに 10 基を揃えるなら、c1 の S4 を諦めるか、S4 の対象を広げるしかない。**統括の推奨は「c1 の S4 を諦め、シナリオごとに題材の数が違うことを事前登録に書く」**。利用者の判断を待つ。
- **c4 の S4 は 6 基**で、候補 18 件のうち 7 件を監査で落とした。落とした理由の多くは「節が理由を述べていない」で、これは節を選ぶ規則（理由を表す語が 2 回以上）の精度の問題である。候補をさらに深く引けば増えるが、そのぶん監査の手間が増える（今回の 41 件で、エージェントの監査に 1 件あたり数分かかっている）。
- 言い換えの点検の閾値 0.25 は **13 件で較正した**ものである。今回の 41 件では、閾値を越えた 14 件のうち作り直しで通った 7 件はすべて監査に通ったか別の理由で落ちており、閾値の下で監査が見つけた漏れは 2 件（0.121・0.122）だった。**この 2 件を捕まえるには閾値を 0.12 まで下げることになり、PE2b の ok（最大 0.154）を落とす。語の重なりだけでは分けられない。**
- 要点（rubric）の質は測っていない。第 4 節の error 4 件はすべて「要点が理由でない」で、これは言い換えではなく `qgen` の指示の問題である。次の手は、要点を作らせたあとに「その要点は理由か、決めごとの言い直しか」を別の模型に判定させることだが、今回は入れていない。
- S9 の 1 段先は**ゲッター 1 段だけ**で、2 段以上（ゲッターを呼ぶ関数を呼ぶファイル）はたどらない。また間接参照が正解に入ったのは開発用では 1 件だけなので、**この仕掛けが問題の難しさをどれだけ変えるかは、この分割では測れない**。
- S9 の c1 は言い換えが 5 件中 3 件落ちる。c1 の S9 が 2 基なのはそのためで、候補を深く引いても語の性質は変わらない。
- 本番用（`test` 分割）の問題は作っていない。`gen/run.sh test` で同じ手順を通したあと、同じ監査が要る。
