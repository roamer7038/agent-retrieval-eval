## 4. 分析モデル

### 4.1 単位と入れ子

- **L2 は 1 セッション＝1 問**。1 セッションは 1 コンテナで、状態は持ち越さない。
- 観測は「問題 × 条件 × 反復」。**問題は条件と交差**し（同じ問題を全ての当てはまる条件で流す）、**題材とシナリオは問題に入れ子**になる（1 問は 1 つの題材・1 つのシナリオに属する）。
- 反復（同じ問題・同じ条件を繰り返す）は、**事前登録で決めた問題の部分集合にだけ**置く（第 6 節）。

### 4.2 モデル

費用と時間（連続量）:

```
log(y) ~ cond * scenario + phrasing + corpus + (1 | question) + (1 | question:cond)
```

- 固定効果: 条件、シナリオ、表し方（identifier / paraphrase）、題材、および **条件 × シナリオ**（H1b・RQ1 の仮説は交互作用である）。
- ランダム効果: 問題（切片）と、**問題 × 条件**（反復がある問題でのみ識別される）。
- 題材は水準が 3 つ（L2）しかないので**固定効果**として扱い、題材の水準についての一般化はしない。

正答（0/1）:

```
correct ~ cond * scenario + phrasing + corpus + (1 | question)
```

混合効果ロジスティック回帰。**天井効果があるときは、同等性の判定を問題を単位にした対応のある差（第 4.4 節）で行い、モデルは記述に用いる**。

L1:

```
nDCG@10 ~ family * phrasing + corpus + (1 | question)
```

系統（family）を単位にした対比を主とし、道具ごとの値は記述として併記する。

### 4.3 交互作用の対比

H1b と RQ1 は交互作用なので、「言い換えでの（混合 − 字句）」から「識別子ありでの（混合 − 字句）」を引いた**差の差**を推定し、95% 区間を出す。H2b も同じ形で、「シナリオ × 条件」の対比を事前に列挙する。

### 4.4 同等性（TOST）

H2a は、**問題を単位にした対応のある差**で行う。問題 q について条件 A・B の正答の割合 ȳ_Aq・ȳ_Bq（反復が無ければ 0/1）をとり、d_q = ȳ_Aq − ȳ_Bq の平均と標準誤差から、±5 ポイントの帰無を両側の 2 つの片側検定で棄却できるかを見る。**クラスタ（問題）を単位にするので、反復による過小な標準誤差にならない**。H1a も同じ形で、幅は ±0.05（nDCG@10）とする。

### 4.5 多重比較の族

- **族は H1a・H1b・H2a・H2b の 4 つ**。Holm の方法を族に適用する。
- 族の中で条件の対を複数比べる場合（A2〜A7 の 6 条件を A1 と比べるなど）は、**その 6 つも族に数える**（H2a の族は 6、H2b の族は 6）。実装では「族 = {H1a の対比} ∪ {H1b の対比} ∪ {H2a の 6 対比} ∪ {H2b の 6 対比}」にまとめて Holm をかける。
- 上に挙げていない対比（題材ごと、シナリオごとの下位の比較、RQ3、道具の使用率、損益分岐）は**すべて探索的**とし、補正せず、区間だけを報告し、「探索的」と明記する。

### 4.6 割り付けどおりの分析と、使ったセッションだけの分析

統括の決定により、**2 本立てで報告する**。

1. **割り付けどおり（intention-to-treat）**: 道具を使ったかどうかに関係なく、条件ごとに全セッションを集計する。**これを主要な分析とする**。
2. **使ったセッションだけ**: 足した道具を 1 回以上呼んだセッションだけを集計する。これは**探索的**であり、選択による偏り（道具が役に立ちそうな問題でだけ使われる）が入ることを明記する。

## 5. 除外基準

セッションは次のときに限り除外する。**除外はすべて件数と理由を条件ごとに報告する**。

| # | 基準 | 扱い |
|---|---|---|
| 1 | ハーネスの失敗（コンテナが起動しない、索引の mount に失敗、API の認証の失敗） | 除外し、**同じ割り付けで流し直す**。流し直した回数を報告する |
| 2 | 時間切れ（1 セッション 25 分） | **除外しない**。時間は上限の値、費用はその時点までの額、正答は誤答として扱う。条件ごとの時間切れの率を主要な結果の一つとして報告する |
| 3 | `answer.json` が無い、または JSON として読めない | **除外しない**。誤答として扱う |
| 4 | MCP のサーバが `connected` にならなかった | 除外し、流し直す。3 回続けて失敗したらその升目を「道具が動かない」として記録し、以降は流さない |
| 5 | API 側の障害（`result_subtype` が `error_during_execution` など） | 除外し、流し直す |
| 6 | 課題の外の道具を使った（`WebFetch`・`WebSearch`・禁じた MCP の道具） | 除外しない。規則違反として記録し、件数を報告する |
| 7 | 正解の誤りが本番の後に見つかった問題 | その問題を**全条件から**外し、外した件数と理由を報告する。条件ごとに外すことはしない |

**判定の順序**: 1・4・5（ハーネスと外部の失敗）だけが除外で、2・3・6（エージェントの振る舞い）は結果である。この区別を動かさない。

## 6. 規模と停止規則

- **問題数 n と反復数 r は、PE5 の分散の推定とシミュレーションで決める**（`pe5.md` 第 4 節の表）。凍結の版に、選んだ n・r とそのときの検出力を書く。
- **反復は問題の部分集合に置く**。事前登録で選ぶ規則: 題材 × シナリオごとに、乱数（種を事前登録）で選んだ 1 割の問題に r 回。それ以外は 1 回。
- **停止規則**: 測定は事前に決めた n × 条件 × r のセッションをすべて流し終えたら止める。**途中で結果を見て止めることも、足すこともしない**。例外は次の 2 つだけで、いずれも起きたら報告する。
  1. **費用の上限**（凍結の版に書く額）に達したとき。そのときは**問題の単位で**打ち切り、打ち切った問題を分析から外す（条件の間で欠けないようにするため）。
  2. **道具の不具合**が見つかり、そのままでは測定にならないとき。直した場合は、その道具の全セッションを流し直す。
- **中間解析は行わない**。較正（PE5）の後に本番の統計量を見るのは 1 回だけである。

## 7. シナリオごとに題材の数が異なることの扱い（重みづけ）

シナリオによって当てはまる題材の数が違う（c4 はコードのシナリオが無く、c2 は文書のシナリオが少ない）。また問題の数も題材によって違う。そのまま平均すると、**問題の多い題材の結論**になってしまう。

| 集計 | 規則 |
|---|---|
| シナリオごとの値 | **題材を等しく重みづけて**平均する（題材ごとに平均してから、題材の平均を平均する） |
| 全体の値 | **シナリオを等しく重みづけて**平均する（シナリオごとの値をさらに平均する） |
| 混合効果モデル | 重みは使わず、題材とシナリオを固定効果として入れ、**推定は周辺平均（EMM）**でとる。EMM は水準を等しく重みづけるので、上の規則と同じ意味になる |
| 道具が当てはまらない組み合わせ | 平均から外す（0 を入れない）。外した組み合わせは 3.2・3.3 の表のとおりに固定し、後から変えない |

**どの表も、重みづけの規則を表題に書く。** 重みなしの平均も付録に載せ、結論が重みづけで変わるかどうかを示す。

## 8. L1 と L2 の役割

| | L1（検索単体） | L2（エージェント経由） |
|---|---|---|
| 問い | 道具は正解を上位に出せるか | 道具を足すとエージェントの費用・時間・正答はどう変わるか |
| 入力 | 質問を事前登録した規則で問い合わせに変換したもの | 課題文（質問と答え方）をそのまま |
| 道具 | 16 種すべて（当てはまるもの） | 系統ごとの代表 1 つ（A2〜A7） |
| 費用 | LLM を使わない（qmd の内部の LLM を除く） | 1 セッションごとに API の費用がかかる |
| 役割 | **道具の検索の質そのもの**を、エージェントの気まぐれから切り離して測る。本番の問題数は費用で縛られないので、全問を流す | **実際に使うときの費用と時間**を測る。予算で縛られるので、問題数は検出力の計算で決める |
| 関係 | L1 の順位が L2 の効果を説明するか（**探索的**）。L1 で良い道具が L2 でも効くとは限らない（使われないことがある） | ― |

**L1 の結果を L2 の代表の選定に使った**（PE3）。したがって L2 の条件の選び方は L1 に依存しており、**L2 は L1 の独立した確認ではない**。この依存を限界として書く。

## 9. 限界（凍結の版に載せるもの）

1. **題材が 4 つしかない**。題材の水準（規模・言語・種類）についての一般化はしない。結論は「この 4 つの題材では」と条件つきで書く。
2. **自作の道具（wikictl）を著者が評価している**。wikictl は c1・c4 にしか当てはまらず、c1 は著者のリポジトリである。この利益相反を明記し、wikictl を除いた分析も併記する。
3. **渡し方が道具ごとに違う**。MCP のサーバは自分の道具の定義と説明を接続時に送る（Serena は 21 個、codebase-memory-mcp は 17 個）。CLI の条件にはこれが無い。**道具の定義の分のトークンを分けて報告する**が、渡し方の差と道具の差は分けられない。
4. **Serena には編集の道具が含まれる**。検索の実験としては余分だが、本来の形を崩さないために残した（`execute_shell_command` だけは記録を迂回するので外した）。
5. **GitNexus は埋め込みを作らないまま**、字句とグラフだけの状態で L1 に入れる。
6. **正解の一部は機械が作り、エージェントが監査した**。人の監査を経ていない部分がある場合は、その範囲と件数を明記する（本番の前に人の監査を済ませるのが前提）。
7. **言い換えの質問には床がある**。L1 では全道具が 0 になる問題が 27%（うち 61/65 が言い換え）ある。作り方を変えると正解の監査をやり直すことになるため、このまま持ち込み、結果として報告する（統括の決定）。
8. **費用の指標はキャッシュの扱いに依存する**。主要な指標はキャッシュが無いとして数え直した額であり、実際の請求額とは異なる（第 2 節）。
9. **1 モデル（Sonnet）の結論である**。Opus・Haiku は本番の後の拡張とする。
10. **トランスクリプトは公開しない**（題材の抜粋を大量に含むため）。道具の呼び出しの記録（コマンド、時間、出力の大きさ）と正解（パスと行の範囲）は公開する。
11. **測定の枠を他の測定と分け合っている**。実時間は、同じ機械で別の測定が動いていると伸びる。本番は 1 つの枠で 1 つの測定だけを動かす（統括の決定）。
