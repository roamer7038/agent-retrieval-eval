# PE2d 要点の質の点検と、テストを除く規則（開発用）

2026-09-21。[PE2c](pe2c.md) の第 6 節「限界と判断が必要な点」のうち、(1) 要点（rubric）の質を測っていないこと、(2) S7 の「テストを除く」がファイルの名前を見ていないこと、(3) c4 の S4 が 6 基しかないこと、の 3 つを生成器の側で直し、開発用の問題を作り直した。本番用の問題は作っていない（事前登録の後に同じ生成器で作る）。題材と固定コミットは PE2b・PE2c と同じ（C1 wikictl 66846e2 ＋ wiki 7a2a507、C2 grafana 39703a2、C3 linux 40288c9、C4 kubernetes/website 4aa397d）。ローカルの Ollama だけを使い、クラウドの LLM は使っていない。

事実と解釈を分けて書く。**監査・札付けをしたのは人ではなくエージェント（Claude）**である。利用者の監査はこれとは別に要る。

## 2. 要点（rubric）の質の点検

### 2.1 何を足したか

S4 の正解は要点の一覧で、採点はその要点を**すべて**述べた回答だけを正解とする（`gen/judge.py`）。だから、理由でない要点（決めごとの言い直し、帰結、但し書き）が 1 つ混ざると、**正しい回答が不正解になる**。PE2c の監査が S4 の 25 基のうち 4 件をこの型の誤り（`error`）としており、言い換えの点検では見つからない（言い換えは正しく、要点だけが誤っている）。

`gen/phrase.py` の段階 1b を足した。

```
qgen (qwen3.8:27b) → 質問と要点
  ↓
rubric (gemma4:31b) 正解が指す行（gold.ref、採点者が見るのと同じ範囲）と質問と要点を見せ、
                    要点ごとに reason / restatement / consequence / caveat / not_in_text、
                    加えて「節が理由を述べているか」を返させる
  ↓ 落ちたら
qgen もう一度（どの要点がなぜ駄目かを伝える） → rubric もう一度 → なお落ちれば候補を捨てる
```

要点を作ったモデルと判定するモデルを分けたのは、同じモデルに自分の書いたものを判定させないためである。判定に見せるのは `qgen` が読んだ節の本文ではなく**正解が指す行**にした。範囲が理由を含んでいない正解（PE2b で 4 件あった `ref_range_excludes_reason`）も、同じ点検で「節が理由を述べていない」として落ちるからである。

点検を入れたのは S4 だけである（`RUBRIC_SCENARIOS`）。答えが理由であるシナリオは S4 だけで、S5（手順）は目的を言い直した要点が同じ誤りにならない。

### 2.2 閾値の較正

較正の集合は **PE2c の phrased な S4 候補 41 件のうち、要点と監査の判定がある 33 件**である（`gold-work/phrased/dev-pe2c/S4.jsonl` に固定した。分割の phrased ファイルは生成器を回すたびに上書きされるため、較正はそれを読まない）。監査の `error_kind` で 3 つに分けた。

| 群 | 件数 | 点検に期待すること |
|---|---|---|
| ok（監査が通した） | 17 | 落とさない |
| 要点・節の誤り（`points`・`point_restates_question`・`point_off_target`・`no_reason_in_section`・`ref_range_excludes_reason` など） | 8 | 落とす |
| 言い換えなど別の理由で落ちたもの | 8 | どちらでもよい（落としても損はない） |

判定は 1 基につき 1 回だけ呼び、同じ答えの上で 18 通りの規則を比べた（`gen/calibrate_rubric.py`、記録は `results/pe2d-rubric-calib.jsonl`）。

| 要点に許す label | 落としてよい割合 | 誤り 8 件のうち落とせた | ok 17 件のうち誤って落とした |
|---|---|---|---|
| reason のみ | 0（＝ 1 つでも駄目なら落とす） | **7** | **5** |
| reason のみ | 0.5 | 2 | 0 |
| reason・caveat | 0 | 7 | 5 |
| reason・consequence・caveat | 0 | 5 | 3 |
| reason・consequence・caveat | 0.5 | 1〜2 | 0 |

採ったのは 1 行目（`RUBRIC_KEEP = {"reason"}`、`RUBRIC_BAD_MAX = 0.0`、`RUBRIC_NEED_SECTION = True`）である。**落とした候補は 1 度引き直され、それでも落ちれば深く引いた別の候補に置き換わる**のに対し、見逃した誤りはそのまま問題になる。この集合では 0.34 と 0.0 は同じ規則になる（要点は 1〜2 個が大半で、1 個駄目なら割合が 0.5 になる）。`section_states_reason` だけで落ちる例はこの 33 件には無かったが、節が理由を述べていない型を捕まえる保険として残した。

誤って落ちた 5 件はすべて、**節の一文の前半と後半を 2 つの要点に分けたもの**だった（例: 「ネットワークポリシーは追加式であるため」＋「評価の順序は結果に影響しない」）。後半を判定者は consequence と読み、監査は「同じ一文なので要点として妥当」と読んでいた。語の重なりのときと同じで、**この 2 つは判定の言葉づかいでは分けられない**。

### 2.3 実際に回したときの数

開発用の S4 候補 53 件（c1 3・c2 21・c4 29）の内訳。

| | 1 回目で通った | 引き直して通った | 落ちた |
|---|---|---|---|
| c1 | 2 | 1 | 0 |
| c2 | 17 | 1 | 3 |
| c4 | 24 | 2 | 3 |
| 計 | **43（81%）** | **4** | **6（11%）** |

引き直しで通った 4 件のうち 3 件は、**帰結の要点が消えて理由だけになった**（`network-policies`・`authentication-mechanisms`・`reconciler-namespace`）。いずれも PE2c では帰結を含んだ要点のまま問題になっていたもので、点検の狙いどおりに直っている。

落ちた 6 件をエージェントが読み直した結果は、**3 件は節が理由を述べておらず落として正しい**（`topology-manager`（QoS クラスの定義を述べるだけ）、`externalname`（生成コードの定型のコメント）、`alerting-get-started-pt5`（初回にダウンロードするという事実だけ））、**3 件は落とさなくてよかった**（`bleve-field-values`（PE2c の監査が ok としていた基）、`swap-memory-management`、`connect-applications-service`）。較正が示した割合（ok の 3 割弱を落とす）と合っている。

### 2.4 点検が見つけられなかったもの

第 5 節の監査は、点検を通った 28 基のうち **3 件**を要点の誤りとした。**3 件とも点検はすべての要点を reason と判定していた**（`pullrequest-comment`（コメントの参照指示「see GrafanaHost」を理由に読み替えた要点）、`pyroscope-troubleshooting`（質問の言い直し）、`horizontal-pod-autoscale-walkthrough-L64`（節は `--cpu-percent=50` の意味を説明するだけで、なぜ 50 かは述べていない））。

つまり、**この点検の再現率は、較正の集合では 8 分の 7 だったが、新しい候補の上では 3 分の 0 だった**。較正の集合は「監査が既に誤りと判じたもの」で、そこには判定者にも分かりやすい誤り（要点が質問の丸写しなど）が多い。新しい候補に残る誤りは、**判定者が節の記述を要点に対応づけてしまう**型で、これは要点と節を突き合わせるだけでは見分けられない。点検は候補の 11% を機械で落とすが、**エージェントや人の監査の代わりにはならない**。

## 3. テストを除く規則をファイルの名前にも広げる

### 3.1 規則

`gen/common.py` の `TEST_PATH` に、ファイルの名前そのものを見る行を足した。

```
| (^|/)test([_-]?(s|ing|util|utils|helper|helpers|support|env|setup|data|fixture|fixtures))?\.(go|c|py|ts|tsx)$
| (^|/)self[_-]?tests?\.(go|c|py)$
| (^|/)fixtures?\.(go|c|py|ts|tsx)$ | \.fixtures?\.[jt]sx?$
```

「名前が `test` で始まる」ではなく**閉じた一覧**にしたのは、題材を見て決めた。grafana の `tester.go`（リポジトリ接続の検査を行う本体）・`testresults.go`・`testjoboptions.go`、linux の `testmode.c`（nl80211 の TESTMODE）は、名前が `test` で始まるが普通のコードである。逆に grafana には `testing.go` が 29 件あり、いずれもそのパッケージのテストのための補助である。

| 題材 | 対象のファイル | 新たに除かれる | 主な名前 |
|---|---|---|---|
| c1 wikictl | 62 | **0** | ―（`_test.go` しかない） |
| c2 grafana | 16045 | **67** | `testing.go` 29・`test-utils.ts` 8・`test_utils.go` 5・`testHelpers.ts` 4 |
| c3 linux | 64535 | **13** | `selftest.c` 8・`test.c` 4 |

質問文（`TEST_EXCL_JA`）にもこの一覧を書き、**正解と質問文が同じ規則を述べる**ようにした。S3・S7 はこの同じ定数を使う（`gen/cand_code.py` の `s3_item`・`s7_go`・`s7_c`）。あわせて、S7 の「型のメソッドをすべて挙げよ」の正解が生成コードのメソッドを黙って外していたのを直した（質問は「すべて」と言っているので、正解も数える。どの型を引くかは手書きのメソッドの数で決めるままにして、引く順が変わらないようにした）。

### 3.2 規則を変えると引き直しになる

候補はプールを混ぜてから前から取るので、**プールから 1 件でも消えると混ぜた順が変わり、その題材の候補はほぼ総入れ替えになる**。実際に入れ替わったのは次の通りで、c1 は 1 件も変わらなかった（除かれるファイルが無いため）。

| | 入れ替わった基 | 理由 |
|---|---|---|
| S1 / c2 | 10（＝全部） | 定義を引くプールから 67 ファイルが消えた |
| S3 / c3 | 6 / 8 | C の索引から 13 ファイルが消えた |
| S7 / c2 | 5（＝全部） | インタフェースの実装・型のメソッドのプールが変わった |
| S2 / c1・c2・c3 | 10 / 22 | 主のファイルの規則が「テストでないコードの追加行」を数えるため |

S5・S6・S7（文書）・S8・S9 は 1 件も変わらなかった。**入れ替わった 31 基はすべて監査し直した**（第 5 節）。

なお、`e2e-playwright/`・`__mocks__/` のような場所の規則は前からあるので、grafana の fake は大半が既に除かれていた。今回の広げ方で実際に正解が変わった例は、S7 の `autogenRuleStore` インタフェースで、実装のうち `notifier/testing.go`・`provisioning/testing.go` にある 2 つの fake が正解から外れた（質問文もそれを述べている）。

## 4. S4 を深く引く

`gen/cand_docs.py` の `N["S4"]` を c4 18 → 30、c2 18 → 26 にした。引く数は**混ぜたプールの先頭から取る数**なので、増やしても既に引いた候補は動かず、後ろに足されるだけである。

- **c4**: 候補 29 件（プールが尽きる）→ 監査を通って **15 基**。目標の 8 基を超えた。
- **c2**: 候補 21 件（プールが尽きる）→ **11 基**。要点の点検が PE2c の ok を 1 件落とした（`bleve-field-values`）ぶんを、深く引いて取り戻した。
- **c1**: dev のプールは 3 件しかない。PE2c の結論（2 基が上限）は変わらない。

**シナリオごとに題材の数が異なる**。S4 は c1 2・c2 11・c4 15、S9 は c1 2・c2 8、S8 は c1 10・c2 3・c4 2 のように、題材が持つ素材の量で決まる。これは道具の比較には影響しない（同じ問題をすべての道具が解く）が、**題材ごとの平均を取るときには重みが変わる**ので、事前登録と分析計画に書く必要がある。

ちなみに **test 分割の c1 の S4 のプールは 11 件**ある（dev は 3 件）。dev のプールが小さいのは、3 回の監査がそこから 9 件を外したからで、題材そのものが尽きているわけではない。本番用の c1 の S4 は 2 基より多くなる見込みがある。

## 6. 本番用（test 分割）が作れるか

**問題そのものは作っていない。**次の 3 つを確かめて、作ったものは捨てた。

1. **候補が引ける**: `cand_code.py`・`cand_git.py`・`cand_docs.py`・`cand_s8.py` を `--split test` で通し、**262 件**の候補を得た（dev は 248 件）。S4 は c1 11・c2 18・c4 30。
2. **開発用と重ならない**: 基の名前の重なり 0 件。正解が指す対象（`gold.ref`・`target`・節・題材のコミット）で見ても **0 件**。項目の割り当ては鍵のハッシュで決まる（`common.split_of`）ので、これは設計どおりである。
3. **端から端まで通る**: 各シナリオ 2〜3 基に絞って `judge.py s9check`・`s9apply`・`phrase.py`・`build.py` を通し、21 候補 → 19 基 → **38 問**を得た。`grade/selfcheck.py` が 38 問 76 セッションで問題 0 件。新しい LLM の呼び出しは 97 回（約 17 分）。

そのあと `gold-work/cand/test`・`phrased/test`・`judge/test` と作った問題のファイルを消した。LLM のキャッシュだけは残してある（本番のときに再利用される）。

**本番用を作る手順**（事前登録の後に行う）。

```sh
ARE_DATA=... gen/run.sh test                               # 候補 → S9 の選別 → 言い換え → tasks/test/pe2.jsonl
# ここで監査を 1 周（S4 は全数、機械の正解は抜き取り）。結果を results/pe2-audit.jsonl に書く
ARE_DATA=... gen/build.py --split test                     # 監査で落ちた基を外して作り直す
grade/selfcheck.py tasks/test/pe2.jsonl <一時ディレクトリ>
```

監査の記録を書いたあとに `gen/run.sh test` をもう一度通すと、落とした基の代わりにさらに別の候補が引かれて未監査の基が増える。**本番では「1 周 → 監査 → `build.py` だけ」で止める**（`cand_*.py` を回し直さない）。今回の開発用でもこの順にしている。

## 7. 限界と判断が必要な点

- **監査したのは人ではなくエージェント**である。第 5 節の判定も誤り率も、人の監査で覆りうる。
- **要点の質の点検は、新しい候補に残る誤りを 3 件とも見逃した**（第 2.4 節）。機械で 11% を落とし、較正の集合では 8 分の 7 を見つけたが、**監査の代わりにはならない**。次の手があるとすれば、要点ごとに「その要点を欠いた回答は不正解にすべきか」を判定させる形（採点の側から見る）で、今回は試していない。
- **点検は ok の 3 割弱を落とす**（較正で 17 件中 5 件、実際に落ちた 6 件のうち 3 件）。深く引ける題材（c2・c4）では引き直しで取り戻せるが、**c1 のようにプールの小さい題材では基の数がそのまま減る**。
- **規則を 1 つ変えると候補が総入れ替えになる**（第 3.2 節）。混ぜる順がプールの中身に依存するためで、監査のやり直しがそのぶん要る。プールの中身に依らない順（項目ごとのハッシュで並べる）にすれば次からは入れ替わりが減るが、**その変更自体が一度は全題材の総入れ替えを起こす**ので、PE2d では変えていない。事前登録の前に一度だけ行うなら、いまが最後の機会である。**判断が必要**。
- **S2 の主のファイルの規則**は、追加のコード行が最多のファイルを選ぶ。新しく足された汎用の部品が、振る舞いを実装したファイルより行数が多いことがあり（第 5 節）、今回 1 件が誤りになった。規則を変えるか、S2 は監査で外し続けるかは**判断が必要**。
- **言い換えに識別子が残る型の誤り**を 1 件見つけた。`leaks()` が使う識別子の一覧は `qgen` が返した語（質問に出てくる語）だけで、節に出てくるが質問には出てこない名前（レシーバの型名など）は点検されない。**候補の `identifiers` に、節・コメントに現れるコードの名前も入れる**のが直し方で、今回は入れていない。
- **`webtest.go` のようなファイル**は、名前の一覧に当たらないので除かれない（`pkg/web/webtest/` はテスト用の HTTP サーバを提供するパッケージである）。名前の規則は「質問文だけで答えを決められる」ことを優先しており、意味の上でのテスト用かどうかとは一致しない。
- **c1 の S4 は dev で 2 基**（PE2c の結論のまま）。test 分割のプールは 11 件あるので、本番では増える見込みがある。
- 言い換えの点検の閾値（0.25）は PE2c から変えていない。今回も閾値の下で答えが漏れた例が 2 件あった（第 5 節の「答えが言い換えに入っている」）。

## 8. PE2c の数値のうち古くなったもの

[pe2c.md](pe2c.md) の第 1 節（要約）の基の数、第 2.4 節（S4 の内訳）、第 4 節（監査）は、この作り直しで変わった。S4 の c1 が 2 基で上限という結論（第 2.3 節）と、S9 の間接参照（第 3 節）は変わっていない。PE2b の S7 の「テストを除く」に関する記述（第 10 節の 4）は、この回で実装した。
